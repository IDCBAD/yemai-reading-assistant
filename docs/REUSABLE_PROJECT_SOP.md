# AI 阅读类项目可复用开发 SOP

> 来源：页脉 v0.1～v0.5 的代码、版本记录、验收证据和相关开发任务。  
> 目的：下次重新开发 Chrome 阅读助手或相似的“前端采集 + Agent 服务 + 本地知识”产品时，不从零重新摸索。

## 1. 适用范围

主体流程适用于：

- AI 阅读、研究、知识整理或浏览器辅助工具。
- 具有外部 Agent/API、流式响应和本地历史的前端产品。
- 需要从原型逐步演进到可迁移、可发布版本的小型项目。

Chrome Extension、Content Script、Side Panel 和 WorkOS 的专项检查放在后半部分。若换成桌面端或普通 Web App，保留问题模型、数据边界和发布门禁，替换平台生命周期即可。

## 2. 总体模型

```text
理解目标
→ 锁定事实与边界
→ 切出最小闭环
→ 前端原型验证
→ 定义数据与协议
→ 分版本实现
→ 分层验证
→ 迁移与退出能力
→ 发布治理
→ 文档收口与归档
```

每个阶段都必须产生一个可以检查的结果，而不是只产生“讨论过”或“代码变多了”。

## 3. 阶段 0：先定义交付结果

### 输入

一个模糊想法，例如“做一个能读网页并和 Agent 对话的 Chrome 插件”。

### 必须确认的决策

1. 谁在什么场景使用？
2. 一次完整成功路径是什么？
3. 哪些数据来自浏览器、用户和 Agent？
4. 哪些能力由插件负责，哪些由 Agent 负责？
5. 什么状态算 v0.1 完成？
6. 什么明确不做？

### 输出

- 一句话产品定义。
- 一个主用户路径。
- MVP 范围和非目标。
- 关键外部依赖及其失败方式。
- 验收标准，而不是功能愿望清单。

### 页脉经验

“网页只是会话的上下文来源，会话按阅读任务组织”一旦明确，跨页面追问、分支、历史和本地存储的设计就都有了稳定锚点。若把一个网页直接等同于一个会话，后续所有跨页面能力都会反复返工。

## 4. 阶段 1：建立事实基线

开发前先盘点当前系统，而不是根据旧文档或对话记忆直接修改。

### 检查表

- 当前分支、HEAD、工作区和远端差异。
- package/Manifest/数据库/协议版本。
- 目录结构、入口和模块职责。
- 可运行的检查、测试、构建与人工回归。
- 凭据、权限、数据事实源和外部平台约束。
- 文档与代码是否漂移。
- 当前版本是“已实现、已验收、已合入还是已发布”。

### 证据优先级

```text
当前代码与测试
> Git 标签和提交树
> 验收记录与构建产物
> Changelog / README
> 历史任务总结
> 人的模糊回忆
```

历史任务非常适合解释“为什么”，不适合单独证明“现在是什么”。

## 5. 阶段 2：用版本梯子切分产品

不要用“做完所有功能”规划版本。每个版本只解决一个能力层级，并为下一层提供结构基础。

页脉的有效梯子是：

```text
v0.1 主路径闭环
  网页资料 → 上下文 → Agent 回答
        ↓
v0.2 连接可交付
  用户配置 → 安全导入 → 明确失败
        ↓
v0.3 数据资产化与找回
  实体存储 → 增量保存 → 全文搜索
        ↓
v0.4 独立知识沉淀
  回答 → 阅读卡片 → 脱离原会话存在
        ↓
v0.5 用户可迁移和退出
  备份 → 恢复 → Markdown 出口
```

### 一个好版本应满足

- 只有一个主目标。
- 有明确的数据或协议前置条件。
- 自动验证和真实环境验证可以分别列出。
- 不把下一个版本的数据模型偷偷塞进当前版本。
- 结束时能形成可回退基线。

## 6. 阶段 3：前端原型先验证产品结构

当界面方向会影响数据模型或核心流程时，先做可交互原型；当只是边距、颜色等局部细节时，直接在现有组件中最小修改。

### 原型应回答的问题

- 信息放在哪里？
- 默认展开还是折叠？
- 窄宽度下是否仍然成立？
- 空、加载、失败、禁用、完成状态是否完整？
- 操作后用户如何确认结果？
- 是否需要新增持久化字段或后端响应？

### 原型隔离原则

- 使用模拟数据。
- 不修改正式 API 和本地数据库。
- 与生产入口分离。
- 设计确认后再写实现计划。
- 原型完成使命后删除或归档，不长期污染仓库。

### 页脉经验

- 多引用不能简单照抄竞品“新引用覆盖旧引用”。最终采用“保留多引用，默认显示最近一条 + 总数 + 查看全部”，既保护证据能力，又避免挤压输入框。
- 回答来源区先做概念图，确认放在回答末尾且默认收起，再实现数据绑定。
- Chrome Side Panel 宽度有限；桌面抽屉、双栏和大卡片在普通网页上成立，不代表在 300～400px 侧边栏中成立。
- 动效应表达状态。Agent 运行时的 Beam 和 Orb 在隔离原型中先确认目的、强度、周期和 reduced-motion，再进入生产代码。

## 7. 阶段 4：先定义数据契约，再接后端

一个上下文型 AI 产品至少要分清：

```text
输入资料
→ 草稿状态
→ 发送时不可变快照
→ Agent 协议投影
→ 回答及来源记录
→ 长期知识资产
```

### 关键问题

- 对象的稳定 ID 是什么？
- 内容是原始资料、有限快照还是来源元数据？
- 哪些状态只在内存，哪些需要持久化？
- 重试读取发送时快照还是当前草稿？
- 分支携带哪些可见上下文？
- “随问题提供”和“Agent 实际引用”能否区分？
- 外部通道切换后，旧远端会话是否还能复用？

### 页脉经验

“本次上下文”只能声明资料已经随问题提供，不能把它展示成“Agent 引用了这些资料”。如果服务端没有返回结构化引用协议，UI 不应制造确定性。

统一 `ContextItem` 后，页面、划词、图片和文件共享包含、排除、失败、删除、详情和发送快照行为。新增类型不应继续在输入框中堆专用分支。

## 8. 阶段 5：通过深接口控制复杂度

外部协议和持久化应藏在窄接口后面，让上层只依赖稳定语义。

### 推荐 Seam

```text
UI
  ↓
应用协调器
  ↓
Transport / Uploader / Repository / Search Session
  ↓
外部 API、浏览器存储或索引实现
```

### 页脉经验

- `WorkosTransport` 让上层不知道流来自 POST 返回还是独立订阅。
- `WorkosFileUploader` 与对话 Transport 分离，因为两者的认证、格式白名单和升级节奏不同。
- UI 保持 `loadWorkspaceState/saveWorkspaceState` 契约，底层可以从整份 JSON 迁移到 IndexedDB 实体表。
- 搜索索引是打开搜索时生成的派生数据，不需要进入数据库 schema。

接口应该隐藏大量协议细节，而不是只把一个大文件拆成多个同样泄漏细节的小文件。

## 9. 阶段 6：实现节奏

### 每个切片

1. 建立独立分支。
2. 写下范围、非目标和验证标准。
3. 先实现纯逻辑与测试。
4. 接入 UI 或浏览器生命周期。
5. 运行小范围测试。
6. 完成整版自动门禁。
7. 完成必须的真实环境回归。
8. 获得确认后再提交/合并。

### 推荐提交边界

- 一个提交只表达一个可回退的能力或修复。
- 迁移、协议和 UI 不要混成无法独立验证的大提交。
- 不把构建缓存、浏览器快照、临时原型和个人凭据提交进仓库。
- 推送、合并、标签和 Release 是四个独立动作；用户授权其中一个不自动授权其他动作。

## 10. 阶段 7：诊断复杂故障

### 诊断循环

```text
复现
→ 找共同故障点
→ 收集最小证据
→ 建立一个可证伪假设
→ 修复根因
→ 增加回归测试
→ 真实环境复核
```

### 不要按表象拆成多个 Bug

页脉曾同时出现“读取页面失败”和“划词没有进入侧边栏”。网页上的浮动按钮已经存在，说明 Content Script 注入成功；两个失败动作都经过 Background，因此共同故障点是消息桥。最终修复 Chrome `runtime.onMessage` 的异步回包模式，而不是分别修改页面抽取和引用 UI。

可复用规则：当多个功能同时失败时，先画调用链，寻找它们最早共享的节点。

### 统一召回、展示和定位

搜索曾出现“结果召回了，但摘要高亮和正文定位错位”。根因是三层使用不同匹配标准。修复方式不是继续修 CSS，而是让索引命中、摘要截取和正文高亮共享真实词边界和位置映射。

可复用规则：检索系统必须对“为什么命中、展示哪里、跳到哪里”使用同一证据。

### 外部 API 故障先隔离层级

WorkOS v1 多轮请求在服务端执行成功，但 SSE 返回旧完成事件。先证明请求提交、远端执行、网络流和前端解析分别发生了什么，再决定新增 v2 Transport。不要把平台问题包装成无休止的前端重试。

## 11. 阶段 8：分层验证

### 11.1 纯逻辑测试

- 状态机、队列、分支和工作页不变量。
- 协议解析、事件归属和终态。
- URL 规范化、来源 ID 和页面版本。
- 搜索分词、结构化字面量和摘要位置。
- 导入校验、合并、事务回滚和安全过滤。

### 11.2 压力和迁移测试

- 大会话、大消息量、产物和来源数量。
- 只修改一条消息时的增量写入范围。
- 迁移中断后再次启动。
- 重复导入幂等。
- 数据库写入失败时整体回滚。

页脉使用 80 个会话、2,000 条消息等规模验证迁移、搜索和备份。压力测试的价值不仅是速度，更是发现“是否误重写其他实体”和“数量是否保持”。

### 11.3 构建级检查

- TypeScript。
- 全量测试。
- Chrome MV3 生产构建。
- ZIP。
- Manifest 版本、名称和权限。
- 构建警告及主分包变化。
- 敏感信息扫描。

### 11.4 真实环境门禁

自动测试无法替代：

- Chrome 扩展重新加载和受限页面。
- Content Script 注入生命周期。
- Side Panel 打开、隐藏、恢复和焦点。
- 真实 WorkOS 多轮、停止、上传和凭据失效。
- 浏览器重启后的持久化。
- 同扩展 ID 数据升级与跨扩展 ID 备份迁移。

把必须由人完成的检查压缩成短、明确的清单；Agent 先代做其余所有验证。

## 12. 阶段 9：数据迁移、备份和退出能力

当用户数据开始有长期价值时，备份不是锦上添花，而是产品边界的一部分。

### 12.1 先分类数据

| 分类 | 示例 | 处理策略 |
| --- | --- | --- |
| 长期业务数据 | 会话、消息、来源、卡片 | 迁移与备份 |
| 设备设置 | Token、当前页、窗口状态 | 通常不进入普通备份 |
| 派生数据 | 搜索索引、缓存 | 不备份，导入后重建 |
| 临时数据 | File、blob URL、SSE 控制器 | 只在内存存在 |
| 远端数据 | Agent 会话、上传文件 | 明确本地操作不控制它 |

### 12.2 迁移规则

- 旧格式必须显式识别，不能把未知对象强制断言成新类型。
- 写入后回读数量或关键不变量。
- 记录中断状态，使下次启动可以恢复。
- 成功迁移后只有一个事实源，避免永久双写。
- 数据库读取失败时，不得把空默认值覆盖回去。

### 12.3 备份规则

- 版本化格式。
- 导出和导入前都验证结构。
- 导入先预览，后写入。
- 默认提供保守、幂等的合并。
- 替换在单个事务中完成并二次确认。
- 凭据不在读取 Seam 上，而不是事后删除。
- 给用户可读出口，例如 Markdown。

### 页脉的两个校验教训

1. `content: ""` 可能是只有图片/文件产物的合法回答。
2. `url: ""` 可能是未绑定网页的合法占位来源。

验证器必须区分：

```text
字段不存在
字段类型错误
字段存在且允许为空
字段存在且必须非空
```

不要用一个 truthy 判断替代领域规则。

## 13. 阶段 10：发布治理

### 四级状态

| 状态 | 最低证据 |
| --- | --- |
| 已实现 | 代码和自动化证据 |
| 已验收 | 自动门禁 + 必须的真实环境回归 |
| 已合入 | 指定本地或远端主线包含提交 |
| 已发布 | 标签 + Release + 可验证安装包 |

### 发布顺序

```text
版本范围冻结
→ 自动检查
→ Chrome/外部服务人工回归
→ 提交与合并
→ 主线复验
→ 标签
→ Release 与附件
→ 回下载和校验
```

不要在 Changelog 中写了版本号以后，就把它描述成已发布。不要因为后续版本吸收了代码，就补称某个早期版本独立发布成功。

### DEV 与生产构建

开发构建必须在名称、版本显示和操作提示中明显带 `DEV`。Chrome 按扩展路径生成不同 ID；同时加载开发和生产目录会造成数据隔离，容易被误判为历史丢失。

## 14. 阶段 11：文档收口

一个新 Agent 应该只需要一个当前入口，而不是在多份带历史时态的文档之间猜测。

### 推荐文档分层

```text
项目交付手册          当前事实与接管路径
领域术语              稳定概念
产品/技术/协议文档     仍有效的专项约束
Changelog             实现变化
archive               版本快照、计划、调查和概念稿
```

### 归档条件

满足任一条件即可归档：

- 计划已经完成。
- 文档记录的是某个版本当时状态。
- 调查结论已经进入现行协议文档。
- 原型或概念稿不参与当前产品。

归档时保留原路径、当前路径、归档原因和指向当前事实的入口；不要只是把文件丢进一个无说明的文件夹。

## 15. Agent 协作 SOP

### Agent 负责查事实

- 目录、代码、测试、Git、标签和文档引用。
- 外部协议当前行为的可复现实验。
- 哪些文件受影响、哪些链接会断裂。

### 用户负责做决策

- 产品范围和取舍。
- 风险接受程度。
- 是否执行真实发布、推送和高风险数据操作。
- 多个合理产品方向之间的选择。

### 一轮良好的协作

1. Agent 先说明目标理解和最小方案。
2. 并行查明环境事实，不让用户手工找文件或提交。
3. 只询问无法从环境得到的决策，并给出推荐答案。
4. 明确影响文件和风险。
5. 实现后说明 What、Why、How。
6. 自动完成能代做的验证，只把真实平台门禁留给用户。
7. 未获授权不扩大到推送、标签、Release 或数据删除。

## 16. 相似项目的建议起步架构

```text
platform/
  页面/系统采集与生命周期
domain/
  Conversation、ContextItem、Source、KnowledgeAsset
application/
  队列、发送、分支、恢复等用例
transport/
  Agent API 与流式协议
storage/
  Repository、迁移、备份
ui/
  原型验证后的组件与状态反馈
```

不要求第一天就建立这些目录，但应尽早建立这些职责边界。页脉当前的 `App.tsx` 体量说明：当协调逻辑增长时，最先要提取的是稳定用例和协议 Seam，不是机械拆 UI 文件。

## 18. 最短版检查清单

如果时间有限，至少守住以下十二项：

1. 先定义主成功路径和非目标。
2. 代码事实优先于历史文档。
3. 先验证窄屏前端原型，再定后端数据。
4. 发送时冻结上下文快照。
5. 区分“提供了资料”和“Agent 使用了资料”。
6. 外部协议放在可替换 Transport 后。
7. 可能成功的写操作不自动跨通道重试。
8. 长期数据、设备设置、派生数据和临时数据分开。
9. 迁移后只保留一个事实源。
10. 校验器区分缺失、类型错误和合法空值。
11. 自动门禁与真实 Chrome 回归分别记录。
12. 实现、验收、合入和发布永远分开表达。
