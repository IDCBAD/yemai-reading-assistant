| 提交 | 目的 | 结论 |

## 2. 官方公开接口

接口来源：影刀 AI WorkOS 智能体的 [API 发布页面](https://aipower.yingdao.com/agents/409b06a1-2e2a-4d8c-af3c-ec831c0c6449/publish-api)。

截至 2026-08-12，页面公开的主要调用链为：

### 创建会话

```http
POST /oapi/agent/v1/agents/{agentId}/conversations
```

响应提供 `conversationUuid`。

### 真流式执行

```http
POST /oapi/agent/v1/conversations/{conversationUuid}/execute/stream
Content-Type: application/json
```

请求正文：

```json
{
  "content": "用户输入",
  "attachments": []
}
```

响应为 SSE，已观察到的事件包括：

- `xybot-run-lifecycle`
- `xybot-message`
- `message`
- `xybot-stream-complete`

事件数据中可以包含 `conversationUuid`、`runId`、`timestamp` 和具体消息数据。

### 非流式异步执行

```http
POST /oapi/agent/v1/conversations/{conversationUuid}/execute/async
GET  /oapi/agent/v1/conversations/execute/result?runId={runId}
```

异步提交会立即返回唯一 `runId`，随后可以轮询结果。实测连续多轮时，不同问题能够获得不同 `runId` 和正确的最终输出。

### 当前未公开的能力

官方页面没有提供以下接口或协议：

- 先异步提交获得 `runId`，再按该 `runId` 订阅增量输出。
- 为 `execute/stream` 显式指定本轮 `runId`。
- 公开的会话级事件订阅与队列提交组合。

没有官方依据时，不应在产品代码中依赖推测出来的 v2 路径。

## 3. 多轮流式接口的真实复现

为了排除页脉解析器和界面状态的影响，诊断时完全按照官方 JavaScript 示例直接调用接口：

1. 创建全新的 `conversationUuid`。
2. 第一次调用 `execute/stream`，要求返回唯一测试文本。
3. 在同一 `conversationUuid` 上第二次调用 `execute/stream`，要求返回另一段唯一测试文本。
4. 只记录事件名称、事件 ID、runId、字节数和脱敏后的文本归属。

观察结果：

| 调用 | HTTP 状态 | 响应表现 |
| --- | --- | --- |
| 第一轮 | 200 | 返回约 33 KB 的完整事件流，包含本轮 runId 和增量文本 |
| 第二轮 | 200 | 仅返回约 190 字节的上一轮 `xybot-stream-complete`，随后连接关闭 |
| 稍后第三轮 | 200 | 返回第二轮的完成事件和 runId，仍然落后一轮 |

WorkOS 后台实际上执行了第二个问题，说明问题不是“请求没有提交”，而是公开流式响应没有把当前 run 的增量事件交给本次 HTTP 连接。

简化后的现象：

```text
请求 A -> 收到 A 的增量内容
请求 B -> 只收到 A 的完成事件；B 在后台执行
请求 C -> 只收到 B 的完成事件；C 在后台执行
```

这解释了页脉曾出现的两个症状：

- “Agent 已结束运行，但没有返回可显示的文本。”
- 查询结果兜底后，当前问题显示了上一轮回答。

## 4. 已排除的假设

### 不是简单的 SSE 文本解析错误

第二轮原始 HTTP 响应本身只有一个旧的完成事件，没有当前轮文本。即使解析器完全正确，也无法从该响应中恢复本轮增量内容。

### `Last-Event-ID` 不能解决

已经测试：

- 请求头 `Last-Event-ID: {上一轮最后事件 ID}`
- 查询参数 `?lastEventId={上一轮最后事件 ID}`
- 将 Redis 风格事件 ID 的序号递增后再提交

三种方式都仍然返回上一轮完成事件，公开接口没有表现出标准 SSE 游标续传行为。

### `130314f` 没有直接修改 WorkOS 流式客户端

该提交主要修改本地工作区结构、阅读会话、标签页和页面快照共享逻辑，没有直接改动当时的 `workosClient.ts`。它更可能通过更稳定地复用远程会话，暴露了已有的多轮接口问题，而不是直接破坏 SSE 解析。

### 异步轮询不是流式替代品

异步接口可以可靠绑定 runId，但只能在完整答案生成后取回结果。前端逐字播放最终文本只是视觉模拟，不属于真流式，也不能改善真实首字延迟。

## 5. 会话模型中已经暴露的问题

稳定基线中的三个入口仍需在下一次重构前重新定义：

| 入口 | 稳定基线行为 | 待解决问题 |
| --- | --- | --- |
| 添加标签页 | 创建新的本地对话；首次发送时创建新的 WorkOS 会话 | 用户容易理解为同一会话的另一个视图 |
| 新建对话 | 替换当前标签页中的本地对话；首次发送时创建新的 WorkOS 会话 | 与“添加标签页”的底层差异不明显 |
| Fork | 复制分支点之前的本地消息；首次发送时创建新的 WorkOS 会话，并补充分支上下文 | 需要明确分支继承多少历史以及远端是否独立 |

`ReadingSession`、本地聊天线程、界面标签页和 WorkOS `conversationUuid` 是四个不同层次，下一次设计不能再让它们隐式一一对应。

推荐先定义数据契约，再修改前端状态：

```text
阅读空间 Reading Workspace
  ├─ 当前网页与引用集合
  └─ 本地聊天线程 Local Thread
       ├─ 一个或多个界面视图 Tab/View
       └─ 远程执行会话 Remote Conversation
```

其中“一个本地线程是否永久绑定一个远程会话”必须由 WorkOS 接口能力决定，而不是由界面名称倒推。

## 6. 下一次重构前必须确认的接口问题

向 WorkOS 确认或提交最小复现时，应直接询问：

1. `execute/stream` 是否正式支持同一个 `conversationUuid` 连续多轮调用？
2. 为什么第二次调用会先返回上一轮的 `xybot-stream-complete` 并关闭连接？
3. 是否存在按 `runId` 订阅增量消息的公开接口？
4. 是否存在官方支持的“先订阅、后提交”调用顺序？
5. SSE 的 `id:` 是否支持游标恢复；若支持，应通过哪个请求头或参数传递？
6. 完成事件是否保证属于本次 POST 创建的 run？
7. 在前一轮刚完成时，服务端是否需要等待会话状态清理，或者显式确认完成？

提交给对方的最小证据应包含：

- 一个脱敏后的 `conversationUuid`
- 第一轮和第二轮不同的测试问题
- 两轮响应中的 runId
- 第二轮仅 190 字节且只有旧完成事件的原始 SSE 片段
- WorkOS 后台能够看到第二轮正常执行的截图

不要提供全局 Token。

## 7. 后续可选架构

只有接口能力确认后再选方案：

### 方案 A：同一远程会话的官方真流式

前提：WorkOS 修复或说明正确的多轮 `execute/stream` 使用方式。

这是首选方案，因为远程会话天然保留历史，页脉只负责页面上下文和交互入口。

### 方案 B：按 runId 订阅真流式

前提：WorkOS 提供公开的提交接口和 run 级订阅接口。

客户端应先建立订阅或先获得 runId，再只消费匹配该 runId 的事件，旧完成事件必须被忽略。

### 方案 C：每轮创建远程会话，本地重建必要上下文

可以获得每轮真流式，但页脉需要把精简后的对话历史或结构化摘要随问题发送。代价是 Token 增加、远程后台会话碎片化，并且上下文压缩责任从 Agent 平台转移到插件。

只有 WorkOS 无法支持多轮真流式且产品必须立即上线时，才考虑该方案。

### 不采用：异步轮询后模拟打字

它不能满足真流式体验要求，也容易掩盖接口延迟和执行归属问题。

## 8. 下一次实现的验收标准

任何新的会话架构至少要通过以下真实接口验收，不能只依赖 mock 测试：

1. 新会话第一轮逐字显示，文本完整且只属于本轮。
2. 同一会话第二、第三轮仍逐字显示，各自 runId 和回答归属正确。
3. 快速连续发送时能够排队，不串流、不覆盖、不显示上一轮结果。
4. 停止生成只停止目标 run，不破坏下一轮会话。
5. 切换标签页时，后台流继续更新正确的本地线程。
6. 新建对话、添加视图和 Fork 的本地/远程会话关系符合产品定义。
7. 页面引用被取消后不发送页面上下文；恢复引用后按协议发送。
8. Token、网页正文和原始 Agent 推理不会写入调试日志。
9. 刷新插件后，不把 `pending` 或 `streaming` 消息误恢复为已完成。
10. 接口返回旧 run 的事件时必须检测并报告，不能把旧回答显示给新问题。

## 9. 工程纪律

- 官方文档未公开的接口不得进入稳定产品代码。
- 接口诊断先使用最小脚本复现，再修改 React 状态和界面逻辑。
- runId 是执行归属的事实标识；没有可靠 runId 关联时，不得用“最新结果”猜测回答归属。
- 流式完成的判断必须同时考虑目标 runId、文本事件和终止事件。
- 每次架构实验从稳定基线创建独立分支，失败后保留结论文档，不保留补丁链。
- Token 只能从用户设置或受控调试授权中读取，不写入源码、测试快照、文档或终端输出。
