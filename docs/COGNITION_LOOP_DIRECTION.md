# 页脉历史产品方向：个人认知循环

> 决策状态：已被“先收藏，再形成认知”部分取代
> 决策日期：2026-08-26
> 取代日期：2026-08-31
> 当前方向：[`COLLECTION_FIRST_DIRECTION.md`](./COLLECTION_FIRST_DIRECTION.md)
> 边界：本文保留当时的判断与原型记录，不再作为当前默认形成路径。独立 Markdown 目录决策仍然有效。

## 1. 核心判断

页脉不再把“增加更多网页阅读功能”作为下一阶段的产品主线。新的目标是：

> 把网页与 AI 对话中真正改变用户理解的时刻，沉淀为可追溯、会演化的本地认知，并在未来相关场景中重新唤醒。

浏览器插件仍然是合适的入口，因为认知的形成和重遇都自然发生在网页阅读过程中；但插件不是最终知识仓库。页脉负责阅读、对话、提炼、连接和修订，独立的本地 Markdown 目录负责长期保存，Obsidian 是首个使用这些文件的外部工具。

## 2. 要解决的问题

当前页脉已经能够组织网页、引用、文件和图片，与 Agent 连续对话，并把完整回答收藏为阅读卡片。继续增加平台抽取、附件格式、批量链接或远端历史同步，可以提高完整度，但不会形成新的产品价值。

现有闭环仍然是：

```text
网页材料 → 与 AI 对话 → 得到回答 → 保存回答
```

它保存了内容，却没有区分以下层级：

1. 网页或作者实际提出的主张；
2. AI 对资料的解释和推演；
3. 用户主动确认后的当前理解；
4. 该理解后来如何被支持、挑战和修订。

下一阶段需要验证的不是“能否生成更多笔记”，而是“AI 对话能否转化为以后会再次参与思考的个人认知”。

## 3. 产品北极星

核心体验不是生成一张漂亮卡片，而是在未来阅读中出现这个时刻：

> 这篇内容可能挑战你以前形成的一个判断，而且提供了一个当时没有考虑的反例。

产品是否成立，应由旧认知能否影响新的阅读、对话和判断来衡量，而不是由卡片数量、笔记字数或关系节点数量来衡量。

## 4. 核心循环

```text
网页与对话
→ 发现认知转折
→ 用户完成一次微型确认
→ 形成个人认知
→ 写入独立 Markdown 目录
→ 未来网页在本地命中旧认知
→ 用户主动比较新旧观点
→ 保持、补充、修订或取代原认知
```

这条“形成 → 确认 → 重遇 → 修订”循环是第一阶段唯一必须完整证明的纵向闭环。

## 5. 领域对象与边界

### 5.1 资料

网页、剪藏、作者观点和未被用户确认的旧笔记属于资料。资料可以提供证据或触发思考，但不自动代表用户认同。

### 5.2 阅读卡片

阅读卡片继续保存一条完整 Agent 回答的可见快照。它回答“这次 AI 说了什么”，不是用户已经掌握的知识，不应改名或直接升级为认知。

### 5.3 认知候选

Agent 在对话中发现可能的认知转折时，可以低打扰地提出认知候选。候选尚未经过用户确认，不进入长期认知目录。

候选不应在每轮回答后出现。值得提示的信号包括：

- 用户纠正了原有理解；
- 一个模糊概念被说清；
- 多个来源之间的矛盾得到解释；
- 用户能够用自己的语言重新表达结论；
- 对话形成了明确的适用条件；
- 一个观点从“听起来合理”变成“知道为什么成立”。

对话结束时可以提供一次复盘，补充过程中遗漏的候选。

### 5.4 认知

认知是用户主动确认的、能够在其他问题中再次参与判断的理解。优先沉淀可迁移的判断原则、因果模型和方法，同时允许具体决策依据与待验证假设。

一条认知至少应表达：

- 我的当前理解；
- 它改变了什么原有认识；
- 为什么这样认为；
- 适用条件和边界；
- 来源网页与形成对话；
- 尚未解决的问题；
- 当前状态。

可能的状态保持克制：待验证、当前认可、存在争议、已被取代。

### 5.5 认知事件

认知不是静态笔记。同一个稳定认知身份可以经历形成、获得支持、遇到冲突、修订边界和被取代等事件。旧版本不得被静默覆盖，因为“为什么改变”本身也是长期资产。

## 6. 用户确认而不是自动收藏

全自动沉淀会批量制造未经理解的 AI 内容；完全手工整理又难以长期坚持。默认采用约 30 秒的微型确认：Agent 生成候选，用户必须进行一次与知识类型匹配的主动加工。

示例：

| 认知类型 | 微型确认问题 |
| --- | --- |
| 概念理解 | 请用自己的话解释它 |
| 因果模型 | 为什么会发生？ |
| 判断原则 | 什么情况下不适用？ |
| 决策知识 | 接受了什么代价？ |
| 待验证假设 | 还缺少什么证据？ |

用户可以暂缓并保存为待验证，但不能仅凭 AI 自动判断进入正式认知目录。

## 7. 独立 Markdown 认知目录

用户从全新目录开始，不导入现有 Obsidian 笔记。所有确认后的认知写入用户明确选择的独立目录，一条认知对应一个普通 Markdown 文件。

目录边界如下：

- 文件使用稳定 `yemai_id` 标识认知身份；
- 页脉只管理自己创建并带有该身份的文件；
- 用户可以在 Obsidian 中阅读和编辑文件；
- 页脉可以重新读取并索引受管文件，但不擅自修改目录中的其他 Markdown；
- 第一阶段不导入旧笔记、不维护主题汇总文件、不做双向同步；
- 即使未来不再使用页脉，认知仍然是可读、可迁移的普通 Markdown。

这一边界的架构理由见 [ADR 0001](./adr/0001-independent-markdown-cognition-directory.md)。

## 8. 旧认知如何重遇

页面打开后不自动把正文或整个认知目录发送给云端 Agent。推荐的隐私与交互边界是：

```text
当前网页
→ 本地提取关键词和语义线索
→ 本地知识索引筛选少量候选
→ 以低打扰方式提示存在相关个人认知
→ 用户主动查看或发起比较
→ 只把必要片段交给 Agent 分析支持、冲突和边界
```

提示分为三级：

1. 普通相关：只改变知识入口的状态；
2. 明显连接：显示少量相关个人认知；
3. 潜在冲突：克制地提示可能挑战了旧判断。

每次最多呈现一至三条，并说明为什么相关。语义相似本身不能证明存在知识联系，也不能成为自动注入 Agent 上下文的理由。

## 9. 交互与视觉方向

现有对话仍是 Side Panel 的主要入口，不先增加知识仪表盘。知识能力优先进入三个界面：

1. 对话中的认知候选；
2. 当前网页的知识脉络；
3. 单条认知详情与演化过程。

视觉上的重点不是全局力导向知识图谱，而是可解释的局部关系与认知演化线：

```text
最初假设
→ 形成理解
→ 获得支持
→ 发现反例
→ 修订边界
→ 当前认知
```

动效只表达形成、唤醒、冲突和修订等状态变化。全局关系图至少等积累足够多的真实认知并证明有额外用途后再评估。

### 9.1 已确认的 A+ 交互结构

2026-08-26 的前端原型确认采用 A+ 方向：以“对话中的内联认知流”为默认结构，吸收专注工作台和局部关系视图中真正必要的部分。

- 认知候选、微型确认和写入结果都留在原对话流中，不打断当前阅读与追问；
- 写入完成后只保留轻量回执，不把知识详情长期展开在 Side Panel 中；
- 旧认知重遇时展示一条可解释的局部关系，说明当前材料为什么与旧认知相关；
- 只有在用户主动比较新旧观点、需要修订或处理冲突时，才临时升起专注工作台；
- 处理完成后工作台退场，用户回到原对话，并看到本次认知变化的紧凑结果；
- 演化时间线按需再次打开，不设置永久分栏，也不让知识面板持续占据聊天空间；
- 认知价值通过“候选 → 确认 → 重遇 → 比较 → 演化”的逐步显现来建立，而不是一次展示全部知识结构。

这意味着 A 是产品的日常形态，B 是复杂任务中的临时模式，C 是单条认知详情里的局部表达方式，而不是三个并列存在的产品方案。

## 10. 第一阶段明确不做

- 不导入现有 Obsidian 笔记；
- 不做双向同步；
- 不自动修改普通 Obsidian 文件；
- 不做全局知识关系图；
- 不做自动主题汇总；
- 不做间隔复习和记忆评分；
- 不做多人协作、账号系统或云同步；
- 不做全自动知识沉淀；
- 不把每条 Agent 回答都变成认知候选；
- 不把批量链接、WorkOS 远端历史同步或更多平台适配作为产品主线；
- 不为这个方向同时重写现有聊天、页面抽取和工作区模型。

## 11. 两周验证标准

在扩大范围前，真实使用应至少满足：

- 完成十条经过主动确认的认知；
- 发生三次带有明确相关原因的旧认知重遇；
- 至少一条认知因新材料被补充、修订或推翻；
- 至少一次明确感到“如果没有页脉，我不会在这里想起以前形成的这个理解”。

如果只有 Markdown 文件和认知数量增长，却没有旧认知影响新的思考，应停止扩建关系图、自动标签和更复杂的检索。这说明闭环尚未成立。

## 12. 下一步

在写完整实现规格前，按以下顺序降低风险：

1. 验证 Chrome Side Panel 选择、持久访问、读取和更新独立目录的可行性及权限体验；
2. 使用模拟数据制作“候选 → 微型确认 → 重遇 → 修订”的窄前端原型（A+ 方向已确认，等待真实使用验证）；
3. 根据原型确定认知、认知事件和 Markdown 的数据契约（已记录在 [A+ 个人认知循环实施规格](./COGNITION_LOOP_SPEC.md)）；
4. 将完整纵向闭环写成正式规格并拆成可独立验证的工单（规格已发布为 [GitHub Issue #3](https://github.com/IDCBAD/yemai-reading-assistant/issues/3)）；
5. 实现后按两周标准进行个人真实使用验证。

目录读写是硬可行性风险，认知确认和重遇是核心体验风险。在这两项得到可运行答案前，不提前建设完整本地 RAG、知识图谱或同步系统。
