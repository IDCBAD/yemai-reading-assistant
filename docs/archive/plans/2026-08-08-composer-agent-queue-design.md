# 输入框内 Agent 状态与队列交互设计

日期：2026-08-08

## 1. 决策摘要

移除对话流中的独立“思考过程卡片”。Agent 的运行反馈改为附着在底部输入框内，同时保持输入框持续可编辑和可发送。

WorkOS Agent 可以接收多条消息并按顺序执行，因此前端不再用 `isStreaming` 阻止后续发送。用户每次发送后，消息立即进入对话流；尚未开始执行的请求显示“排队中”。

## 2. 目标

- 输入框在 Agent 运行期间保持可编辑、可发送。
- 用小型 Orb 和液态玻璃边缘表达当前运行状态。
- 让用户明确看到当前任务和排队数量。
- 用户发送的消息立即进入对话流，并获得“排队中”反馈。
- 停止当前任务和发送新消息使用独立按钮。
- 答案从首个 token 开始直接进入消息流，不插入独立思考卡片。

## 3. 非目标

- 不改变 WorkOS 后端的排队机制。
- 不重做整个侧边栏视觉主题。
- 不把 Orb 当作真实推理过程或进度百分比。
- 不在本阶段增加任务优先级、拖拽排序或批量取消队列。
- 不把 Liquid Glass 铺到所有消息和页面组件。

## 4. 当前实现约束

正式项目目前在两个位置禁止排队发送：

1. `Composer.tsx` 只有在 `!isStreaming` 时才允许 Enter 发送。
2. `App.tsx` 的 `sendMessage()` 在 `isStreaming` 时直接返回。

当前 `streamsRef` 以 `conversationId` 为键，每个会话只能保存一个 `AbortController`。若要让同一会话存在多个运行或排队请求，需要改为按请求或 assistant message 标识管理。

## 5. 输入框结构

输入框沿用现有三层结构：

1. 顶部 Tab 和会话操作栏。
2. 中部可编辑 textarea。
3. 底部运行状态和操作工具栏。

底部工具栏从左到右为：

- 28-32px `ThinkingOrb`，仅在当前会话存在运行任务时显示。
- 当前状态文字，例如“正在组织回答”。
- 队列汇总，例如“2 条排队”；没有队列时不显示。
- 停止当前任务按钮，仅在存在运行任务时显示。
- 发送按钮，只要草稿内容有效就保持可用。

停止和发送是两个独立操作。运行期间不能用停止按钮替换发送按钮。

## 6. 视觉规则

- 页面主题保持浅色。
- 输入框外壳使用冷白透明材料、1px 内高光和轻微冷色阴影。
- 单一主要强调色继续使用现有钴蓝。
- Orb 尺寸保持 28-32px，不成为独立内容块。
- Border Beam 只在存在运行任务时沿输入框边缘运动。
- 边缘折射可以有极弱的光谱色，但不能形成紫色 AI 光晕。
- 文本区域对比度必须优先于玻璃透明度。
- 输入框高度不因 Orb、队列数量或状态文字而跳动。

网页端效果是对 Apple Liquid Glass 材料语言的近似，不声称使用 Apple 官方 Web 组件。

## 7. 状态模型

每个 Agent 请求具有以下 UI 状态：

- `queued`：消息已发送给前端或 WorkOS，等待开始执行。
- `running`：当前请求正在读取页面、调用工具或等待首个 token。
- `streaming`：答案 token 正在进入消息流。
- `complete`：答案完成。
- `stopped`：用户停止了当前请求。
- `failed`：请求失败。

当前 Orb 只表示活动会话中最早的 `running` 或 `streaming` 请求。队列数量由该会话中 `queued` 请求的数量派生。

Orb 形态映射：

- 读取页面或创建会话：`searching`。
- 等待首个 token：`connecting`。
- 工具活动或组织答案：`weaving`。
- 持续输出答案：`shaping` 或降低强度的稳定状态。

Orb 是运行状态指示器，不显示百分比，也不暗示模型暴露了真实思维链。

## 8. 消息与队列数据流

1. 用户按 Enter 或点击发送。
2. 前端立即把 user message 加入当前会话，并清空草稿输入。
3. 同时创建与该 user message 对应的 assistant placeholder。
4. 如果当前会话没有运行请求，该 placeholder 进入 `running`；否则进入 `queued`。
5. user message 立即出现在消息流中。对应请求为 `queued` 时，在它下方显示低存在感的“排队中”。
6. WorkOS 开始处理该请求后，placeholder 从 `queued` 转为 `running`，输入框 Orb 和状态文字同步更新。
7. 首个 token 到达后，placeholder 转为 `streaming`，答案直接在消息流中展开。
8. 请求结束后转为 `complete`。若仍有队列，Orb 直接切换到下一请求；若队列为空，输入框在 180-220ms 内恢复空闲状态。

前端需要为 user message 与 assistant placeholder 建立稳定关联，避免多个排队请求的状态错配。

## 9. 停止与异常语义

### 停止当前任务

- 停止按钮只终止当前正在运行的请求。
- 已排队请求继续保留并按顺序执行。
- 被停止的请求在消息流中显示“已停止”。
- 当前任务停止后，下一条排队请求自动成为运行任务。

### 请求失败

- 当前请求标记为 `failed`，保留重试入口。
- 失败不自动清空草稿或其他排队消息。
- 前端不主动取消后续排队请求；当前失败状态收敛后，下一条排队请求成为运行任务。
- 认证失败时沿用现有设置抽屉和 Token 提示。

### 页面读取失败

- 当前消息仍可仅使用问题和引用发送。
- 页面读取问题继续由现有 SourceBar 或 page issue 展示，不占用输入框运行状态区域。

## 10. 动效规则

- 发送按钮按压反馈：100-160ms。
- 状态文字切换：150-200ms，使用 opacity 和最多 2px blur。
- Orb 阶段切换：约 300-500ms，允许轻微形变。
- 输入框边缘 Beam：慢速连续运动，只在存在运行任务时出现。
- 队列数字变化：180-220ms，不改变工具栏布局宽度。
- 所有频繁操作保持即时；键盘发送不增加阻塞动画。
- `prefers-reduced-motion` 下停止 Orb、Beam 和形变，只保留静态状态文字与颜色。
- `prefers-reduced-transparency` 或不支持 `backdrop-filter` 时使用高对比实体背景。

## 11. 组件边界

### Composer

负责 textarea、Orb、当前状态、队列汇总、停止和发送操作。只接收派生后的运行摘要，不自行管理 WorkOS 请求。

### App / 请求协调层

负责发送多个请求、维护每个请求的 controller、状态变化和当前会话队列摘要。

### MessageList

负责立即显示 user message、排队状态、streaming answer、停止、失败和重试。它不再渲染大尺寸思考卡片。

### ThinkingOrb 适配层

把项目的请求阶段映射到 `thinking-orbs` 的视觉状态，并统一处理尺寸、暂停、reduced motion 和性能降级。

## 12. 测试范围

### 单元测试

- 第一条消息直接进入运行状态。
- 运行期间发送第二、第三条消息时进入排队状态。
- 队列数量派生正确。
- 当前请求完成、停止或失败后，下一条请求正确接续。
- 停止当前请求不会清除排队请求。
- 多个 Tab 的队列状态互不污染。
- 页面刷新和本地恢复不会把终止的请求错误恢复成运行中。

### 组件测试

- 运行期间 textarea 仍可编辑。
- 有内容时发送按钮保持可用。
- 停止按钮和发送按钮同时可见且具有独立 accessible name。
- Orb 和状态文字正确响应运行摘要。
- 队列消息立即显示“排队中”。
- reduced motion 和透明度降级正确。

### 浏览器验证

- 400px 侧边栏下文本、状态、停止和发送按钮不拥挤。
- 320px 最小宽度下工具栏不溢出。
- 连续快速发送三条消息时顺序稳定。
- 切换 Tab 后，各自的 Orb、队列数量和输入草稿正确。
- 控制台无错误或 React key/state 警告。

## 13. 验收标准

- 对话流中不再出现独立思考卡片。
- Agent 运行时输入框仍然可以编辑和发送。
- 用户消息发送后立即进入对话流。
- 排队消息具有明确但低干扰的“排队中”状态。
- 输入框同时显示当前 Agent 状态和排队数量。
- 停止当前任务不会阻止发送，也不会清除队列。
- Orb 保持小尺寸，并且只承担运行状态反馈。
- 视觉与现有浅色产品一致，没有黑色场景或强紫色光晕。

## 14. 高强度彩虹 Border Beam 修订

本节覆盖第 6、10、13 节中“克制”“轻微”或“降低外圈折射光”的旧强度描述。用户在真实侧边栏验证后明确要求：Agent 运行期间，整个输入框边缘的动态彩虹效果必须强烈、清晰，并且可以第一眼识别。

### 视觉目标

- 彩虹 Beam 沿输入框完整外轮廓运动，包括顶部、底部、左右边和四个圆角。
- 光束必须具有完整彩虹色相，而不是目前接近普通蓝色描边的 `ocean` 配色。
- Agent 运行时，边缘光在正常屏幕亮度下无需靠近观察即可识别运动方向。
- 输入框内部仍保持浅色冷白玻璃材料，不改成黑底或霓虹暗色主题。
- 高强度只作用于输入框外缘，不给整个侧边栏、消息卡片或页面边缘增加彩虹光。
- 空闲状态恢复为中性蓝灰边框；彩虹 Beam 仅在 `running` 或 `streaming` 时出现。

### Border Beam 参数基线

- `size="md"`：使用面向卡片和大容器的完整边缘预设，不再使用按钮尺寸的 `sm`。
- `colorVariant="colorful"`：启用完整彩虹光谱。
- `theme="light"`：继续适配浅色输入框。
- `strength={1}`：使用完整组件强度。
- `duration={2.6}`：约 2.6 秒环绕一周，运动必须明显但不能闪烁。
- `brightness={1.5}`：增强浅色背景下的光束可见度。
- `saturation={1.9}`：让红、黄、绿、青、蓝、紫在白色背景上保持可辨认。
- `hueRange={70}`：扩大动态色相变化范围。

项目 CSS 允许在 `.composer-beam` 上使用该组件公开的 CSS 变量放大浅色预设：

```css
.composer-beam {
  --beam-stroke-opacity: 3.2;
  --beam-inner-opacity: 1.7;
  --beam-bloom-opacity: 1.55;
}
```

这些倍率仅补偿 `border-beam` 浅色主题自带的低不透明度，不允许改动或复制 npm 包内部实现。

### 图层与边界

- 输入框自身的结构边框透明度需要降低，避免覆盖彩虹 Beam。
- Beam 图层必须紧贴输入框外轮廓，不能错误地出现在应用窗口顶部或整个侧边栏外缘。
- 彩虹 Bloom 需要在边缘附近形成约 4-8px 的可见光晕，并保持在 `.composer` 的内边距范围内，不得被视口裁切。
- Beam 不得截断 Tab、停止按钮、发送按钮或 textarea 的焦点轮廓。
- 在 320px 和 400px 宽度下使用相同的色彩与速度参数，不因窄屏降为蓝色单色。

### 动效与无障碍

- 彩虹环绕是 Agent 活动状态的装饰性强化，Orb 和文字仍是主要语义反馈。
- `prefers-reduced-motion: reduce` 下停止角度旋转，保留一圈高对比静态彩虹边缘。
- Beam 的显示和隐藏使用组件自带淡入淡出；键盘发送不等待淡入动画。
- 动画不得改变输入框尺寸、触发页面布局位移或阻塞点击。

### 修订后的验收标准

- Agent 运行时，截图和肉眼均能清楚看到彩虹边缘，而不只是蓝色描边。
- 连续观察 1 秒内可以识别光束正在沿完整外轮廓运动。
- 彩虹效果只包围底部输入框，不包围整个页面。
- 空闲后彩虹效果淡出，中性输入框边框恢复。
- 320px、400px 和 reduced-motion 三种验证状态均无裁切、溢出或文字对比度回退。
