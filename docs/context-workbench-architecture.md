# 统一上下文工作台

## 为什么要统一

页脉的输入区会逐步接入当前网页、划词、图片、文档、链接和历史记忆。如果每种来源各自维护一套状态和组件，新增能力时就会不断叠加特殊分支，也很难保证“是否包含、准备状态、删除、查看详情、发送后留存”这些行为一致。

因此，输入区统一使用 `ContextItem` 作为上下文对象。UI 只负责呈现这种对象，发送链路再把它转换成网页协议、选中文字和附件参数。

## 数据模型

```ts
type ContextItem =
  | PageContextItem
  | SelectionContextItem
  | FileContextItem
  | ImageContextItem
  | MemoryContextItem
  | LinkContextItem;
```

所有对象共享以下字段：

- `id`：对象在输入工作台中的稳定标识。
- `kind`：来源类型。
- `included`：本轮是否允许使用该来源。
- `status`：`preparing`、`ready` 或 `failed`。
- `createdAt`：创建时间。
- `issue`：失败原因或补充提示。

## 生命周期

1. 当前页变化、用户划词或添加附件时，转换为 `ContextItem` 放入 `conversation.draftContextItems`。
2. 用户可以在统一工作台中查看详情、包含或排除来源。除“当前页”外，上下文对象可以删除。
3. 点击发送时，仅选择本轮包含且可用的对象，并创建深拷贝快照写入 `message.contextItems`。
4. Agent 请求从消息快照中读取页面、划词和附件，避免输入区后续变化影响已经发送的问题。
5. 发送成功后，当前页和被排除或失败的对象继续保留；已发送的划词与附件从草稿区清除。
6. 回答来源追溯和会话分支都优先读取消息快照，并兼容旧消息字段。

## 附件的内存边界

- 浏览器存储只保存附件元数据和远程地址，不保存原始 `File` 或本地 `blob:` 预览地址。
- 上传失败时，原始 `File` 仅保留在当前 Side Panel 的内存映射中，因此可以原位重试而不必重复选择。
- Side Panel 关闭或重新加载后，内存映射会自然释放；再次重试时要求用户重新选择原文件，并复用同一个上下文对象。
- 拖拽、文件选择和粘贴最终都进入相同的附件创建与上传链路，避免形成三套状态。
- 附件发送后保留上传通道元数据，消息中的文件令牌可以展示文件类型、大小和上传通道，但不会在后台解析文件内容。

## 回答划词引用

回答正文中的选区可以创建 `origin: 'assistant'` 的 `QuoteReference`，随后仍转换为统一的 `selection` 上下文对象。它与网页划词共享包含、排除、删除和发送快照行为，但来源标识指向原回答消息，不伪造网页网址。

这项交互不引入富文本编辑器：正文仍由 Markdown 渲染，选择完成后只显示一个临时的“添加到对话”操作；点击后才把纯文本选区放入上下文工作台。

## 当前页的特殊规则

- 同一网址刷新标题或读取状态时，保留用户的包含或排除选择。
- 切换到新网址时，默认包含新的当前页。
- 页面正文读取失败时，仍可保留网址作为来源，不伪装成已读取全文。
- 当前页不能从工作台删除，只能临时排除；这样用户可以随时恢复引用。

## 兼容策略

工作区存储版本升级为 v5。加载 v1 到 v4 数据时，会把旧的 `draftQuotes`、`draftAttachments` 和 `draftPageReference` 转换成 `draftContextItems`。旧消息中的 `references`、`attachments` 和 `pageContext` 仍可读取；新消息以 `contextItems` 为准。

## 后续扩展

`memory` 和 `link` 已进入类型与展示层，但还没有创建入口和 Agent 传输协议。后续接入时应补齐：

1. 对象创建器与交互入口。
2. Agent 请求中的明确协议映射。
3. 回答来源追溯规则。
4. 存储迁移和单元测试。

不要直接在 `Composer` 中增加新的专用卡片。
