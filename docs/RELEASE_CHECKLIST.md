# 页脉发布检查清单

这份清单用于在创建稳定版本前进行可重复的人工验证。自动化测试负责数据模型和核心逻辑，真实 Chrome 检查负责 Side Panel、焦点、网页注入和浏览器生命周期。

## 1. 发布准备

- [ ] 确认发布目标、版本号和主要变更。
- [ ] `package.json` 与 `wxt.config.ts` 中的版本号一致。
- [ ] 当前分支基于最新 `main`，工作区没有无关改动。
- [ ] 更新 `README.md` 与 `CHANGELOG.md`。
- [ ] 确认没有凭证、Token、个人 UUID、调试日志或临时文件进入提交。

## 2. 自动检查

```bash
npm install
npm run check
npm test
npm run build
npm run zip
```

- [ ] TypeScript 类型检查通过。
- [ ] Vitest 测试全部通过。
- [ ] Chrome MV3 生产构建成功。
- [ ] ZIP 安装包生成成功。
- [ ] 记录不阻塞发布的构建警告。

## 3. Chrome 人工回归

### 安装与连接

- [ ] 从 `.output/chrome-mv3` 重新加载扩展，没有 Manifest 错误。
- [ ] 点击扩展图标可以打开 Side Panel。
- [ ] 全新安装时 Agent UUID 为空，默认选中实验性实时连接。
- [ ] 旧配置升级后不会继续沿用程序曾隐式提供的 Agent UUID。
- [ ] 打开并登录影刀 AI WorkOS 后，“从 WorkOS 获取”可以填入三项登录信息，但不会自动保存。
- [ ] 未打开 WorkOS、未登录、字段缺失和 WorkOS 页面刚刷新时都有明确错误提示，且原有表单内容不被覆盖。
- [ ] 设置页可以保存并测试实验性实时连接，测试中、成功和失败状态清晰可辨。
- [ ] 如需继续提供官方 API，单独验证其连接，并记录当前多轮流式限制。
- [ ] 验证实验性实时连接的附件上传。
- [ ] 关闭并重新打开浏览器后，连接设置仍可恢复。

### 网页与引用

- [ ] 普通网页能够显示正确的标题、URL 和图标。
- [ ] 页面正文可以读取并随第一条相关问题发送。
- [ ] SPA 页面跳转后，当前页标题和上下文能够更新。
- [ ] 普通划词入口可以加入精确选中的文字。
- [ ] 智能框选启动后 Side Panel 自动隐藏。
- [ ] 鼠标移动时可以识别正文、左侧导航和右侧目录等内容块。
- [ ] 点击内容块后，引用进入输入区并恢复 Side Panel。
- [ ] 按 `Esc` 或点击关闭按钮能够取消框选并恢复 Side Panel。
- [ ] 浏览器内置页面等不可注入页面给出克制、明确的提示。

### 输入与回答

- [ ] 点击首页建议后，文字进入输入框且输入框获得焦点。
- [ ] `Enter` 发送，`Shift + Enter` 换行。
- [ ] 回答可以流式显示、停止、重试和复制。
- [ ] 用户问题可以复制并重新编辑到输入框。
- [ ] Markdown 标题、列表、表格、链接和代码块显示正常。
- [ ] 工具运行面板不暴露原始参数、输出或思维链。

### 附件与上下文

- [ ] 文件选择、上传状态、失败重试和移除正常。
- [ ] 可以在输入框粘贴剪贴板图片。
- [ ] 图片缩略图、悬浮预览和大图查看正常。
- [ ] 页面、引用、文件和图片可以在发送前分别启用或移除。
- [ ] 回答下方的本次上下文来源与实际发送内容一致。

### 会话与恢复

- [ ] 新建、切换和关闭工作页正常。
- [ ] 历史会话可以打开、归档和恢复。
- [ ] 从已完成回答创建分支后，来源关系和上下文正确。
- [ ] 刷新扩展或重新打开浏览器后，会话、草稿和打开工作页能够恢复。
- [ ] 10 个工作页上限及对应提示正常。

## 4. 发布 GitHub Release

- [ ] 发布分支已经合并到 `main`。
- [ ] 在合并后的 `main` 提交上创建带说明的版本标签。
- [ ] 创建 GitHub Release，并使用 `CHANGELOG.md` 编写 Release Notes。
- [ ] 上传 WXT 生成的 Chrome ZIP，而不是提交构建目录。
- [ ] 下载 Release 附件并确认可以正常解压。
- [ ] 记录 Release 页面、标签提交和安装包 SHA-256。

## 5. 回退原则

如果发布后出现阻塞使用的问题：

1. 保留已有标签和 Release，不重写版本历史。
2. 从对应标签复现问题并创建修复分支。
3. 修复后发布新的补丁版本，例如 `v0.1.1`。
4. 在旧 Release 中标记已知问题和推荐升级版本。
